# تنظیم برای اتصال‌های زیاد

مسیر موردنظر: کاربران OpenVPN به TCP/2083 ایران وصل می‌شوند؛ ایران ترافیک را
با ICMP به خارج می‌فرستد؛ خارج به OpenVPN در `127.0.0.1:2083` وصل می‌شود.

فایل‌های `config-client-capacity-sample.json` برای ایران و
`config-server-capacity-sample.json` برای خارج نقطهٔ شروع برای ۸ هسته و
۱۶ گیگابایت RAM هستند. آی‌پی نمونه و رمز را جایگزین کن؛ رمز دو سمت یکسان باشد.
هر فایل را با `chmod 600` محافظت کن. دستور اجرا:

```sh
# خارج
./pingtunnel-echo -c server.json
# ایران
./pingtunnel-echo -c client.json
```

هر دو برنامه مجوز raw ICMP لازم دارند. پیش‌نیازهای فایروال و پاسخ خودکار کرنل
در `ECHO_MODE.md` آمده‌اند. برنامه خودش sysctl یا فایروال میزبان را تغییر نمی‌دهد.
برای systemd مقدار `LimitNOFILE=65536` مناسب این نقطهٔ شروع است. روی سرور اختصاصی
۸ هسته می‌توان `GOMAXPROCS=8` گذاشت. اگر OpenVPN هم روی همین سرور است، CPU آن را
هم در محاسبه لحاظ کن. `GOMEMLIMIT=8GiB` یک حد نرم برای GC است، سقف قطعی RAM نیست؛
برای OpenVPN و بافرهای شبکهٔ کرنل حافظه باقی بگذار.

## تغییر اندازهٔ بافر و پنجره

دو گزینهٔ جدید فقط روی **کلاینت ایران** تنظیم می‌شوند و از طریق فیلدهای موجود
پروتکل به سرور منتقل می‌شوند:

| JSON | CLI | پیش‌فرض قبلی | نمونهٔ اتصال زیاد |
|---|---|---:|---:|
| `tcp_buffer_bytes` | `-tcp-buffer-bytes` | 1048576 | 262144 |
| `tcp_window_frames` | `-tcp-window-frames` | 20000 | 512 |

صفر یعنی پیش‌فرض قبلی. محدودهٔ بافر ۸۸۸ بایت تا ۱۶ MiB و پنجره ۱ تا ۲۰۰۰۰ فریم
است. مقادیر خارج از محدوده پیش از تخصیص بافر یا اتصال به مقصد رد می‌شوند.
تنظیمات پیش‌فرض برنامه تغییر نکرده‌اند. برای این تنظیم‌ها نیازی به تغییر قالب
protobuf نیست. فیلدهای قدیمی v2 مانند `tcp_bs` همچنان نامعتبرند.

با این نمونه، تخصیص اولیهٔ FrameMgr برای هر اتصال از حدود ۳٫۱۲ MB به ۰٫۵۵ MB
کاهش یافت؛ حدود ۸۲٪ کمتر. این مقدار شامل رشد فریم‌های درحال انتقال، صف‌ها،
goroutineها، GC و حافظهٔ socketهای کرنل نیست. `maxconn:4096` تعداد اتصال تونل
را محدود می‌کند، نه تعداد کاربران OpenVPN. ۲۰۰۰ کاربر الزاماً ۲۰۰۰ اتصال نیستند.

پنجرهٔ کوچک‌تر می‌تواند سرعت یک اتصال روی مسیر پرتاخیر را محدود کند. برای
مثال ۵۱۲ فریم با payload حدود ۸۸۸ بایت روی RTT برابر ۱۰۰ms سقف نظری حدود
۳۶Mbps برای **یک اتصال** می‌دهد؛ در عمل هزینهٔ پروتکل و ازدحام آن را کمتر می‌کند.
اگر همهٔ کاربران پشت یک اتصال TCP مشترک multiplex شوند، این نمونه مناسب هدف
۱Gbps نیست. در آن حالت و برای جریان‌های بزرگ، پنجره را با اندازه‌گیری RTT،
افت بسته و حافظه افزایش بده؛ صرفاً بزرگ کردن همهٔ بافرها jitter را حل نمی‌کند.

## شواهد و حدود اعتبارسنجی

۲۰۰۰ اتصال TCP هم‌زمان با ChaCha20 و Echo روی raw ICMP در namespace محلی
آزمایش شدند. هر اتصال یک پیام متمایز را برگرداند، باز ماند و پس از رسیدن به
اوج هم‌زمانی دوباره تبادل پیام کرد. این آزمون OpenVPN واقعی یا مسیر ایران–خارج
را شبیه‌سازی نمی‌کند و سنجش throughput برابر ۱Gbps نیست. سیستم تست هر دو سمت
تونل را در یک پردازش اجرا می‌کند؛ بنابراین heap آن با RAM یک سمت تولید یکسان نیست.

اجرای دوباره با Go مشخص‌شده در `go.mod`:

```sh
go test -run '^$' -bench '^BenchmarkTCPResourceAllocation$' -benchtime=100x
go test -c -o /tmp/pingtunnel-capacity.test .
unshare --user --map-root-user --net sh -c '
  set -e
  ip link set lo up
  sysctl -w net.ipv4.icmp_echo_ignore_all=1
  GOMAXPROCS=8 PINGTUNNEL_E2E_REQUIRE_REAL_ICMP=1 \
    PINGTUNNEL_E2E_CONNECTIONS=2000 /tmp/pingtunnel-capacity.test \
    -test.run "^TestE2E_HighConcurrency$" -test.v -test.timeout=5m
'
```

برای قبول ظرفیت واقعی، روی دو سرور تعداد کاربران، throughput مفید، نرخ
بسته، retransmit، CPU، RSS و RTT/jitter را قبل و حین بار اندازه بگیر. لینک
۱Gbps به معنی ۱Gbps ترافیک مفید OpenVPN نیست؛ Echo Reply در جهت مقابل payload
کامل دارد و سربار ICMP، رمزنگاری و انتقال مجدد هم اضافه می‌شود. اشباع مسیر و
صف‌ها را باید با نرخ قابل‌تحمل همان مسیر و حفظ ظرفیت آزاد کنترل کرد.

## تشخیص‌پذیری و قطع ping

این تنظیم مصرف منابع را کمتر می‌کند؛ ICMP را غیرقابل‌تشخیص نمی‌کند. نوع بسته،
اندازه، نرخ و درخواست‌های دوطرفه برای ناظر شبکه قابل مشاهده‌اند. تغییر بافر یا
رمزنگاری تضمین جلوگیری از مسدودشدن IP نیست. قطع ping ممکن است از محدودیت نرخ
ICMP، افت مسیر، فایروال، پاسخ کرنل غیرفعال یا فیلتر اپراتور باشد؛ از روی یک
علامت نمی‌توان علت را DPI اعلام کرد. قابلیت عبور از DPI در این تغییر آزمایش نشده است.
